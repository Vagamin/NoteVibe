# Чек-лист выпуска NoteVibe

Перед каждым релизом проверяйте по порядку. Цель: не допустить поломки базы у пользователей.

## Миграции базы (главное правило)
- Миграции в `lib/data/schema.dart` только добавляются в КОНЕЦ списка.
- Существующую миграцию нельзя менять, переставлять или удалять.
- Порядок 1.1.0–1.2.x уже «заморожен» (`test/data/migrate_test.dart`). Тест упадёт, если порядок сломан.
- Новую схему описывайте отдельной миграцией, а не правкой старой.

## Перед сборкой
1. `flutter analyze --no-pub` — без ошибок.
2. `flutter test --no-pub --concurrency=1` — все тесты проходят.
3. Проверка на копии рабочей базы: открыть копию `notevibe.db` через приложение (или тест), убедиться, что список читается и заметка создаётся.
4. Для миграций: резервная копия `notevibe.db.bak-vN` создаётся перед обновлением схемы.

## Сборка и подпись
5. Поднять версию: `pubspec.yaml` и `lib/app_version.dart`.
6. `flutter build apk --release --split-per-abi --no-pub`
7. `flutter build windows --release --no-pub`
8. `powershell -ExecutionPolicy Bypass -File tools\portable\build_portable.ps1 -SkipFlutterBuild`
9. Проверить подпись APK: `apksigner verify --print-certs` — должен быть ключ релиза (SHA-256 `7cc9db28…`).

## Публикация
10. Commit и push в `main`.
11. Описание релиза писать в файл UTF-8 и передавать `--notes-file`. Никогда не передавать кириллицу аргументом в PowerShell: текст портится (так были испорчены описания 1.0.5–1.2.2).
12. Перед публикацией проверить файл описания: нет символов `�`, нет «mojibake» вроде `ХИт`. Тест `test/release/notes_encoding_test.dart` проверяет папку `release/`.
13. Если релиз плохой, оставить описание с предупреждением (без `--prerelease`, по решению владельца).

## Версии
- Новая стабильная линия начинается с **1.0.0**, название релиза: **NoteVibe 1.0.0 — stable**, тег: `v1.0.0` (без суффикса stable в SemVer).
- Внутренний Android build number не сбрасывать: первый stable — `+33`, arm64 split versionCode — `2033`.
- Перезапуск нумерации не сбрасывает миграции или данные. Существующие установки 1.4.0 переходят вручную: SemVer-проверка не считает 1.0.0 новее.
- Новая функция — MINOR, исправление — PATCH, глобальное изменение — MAJOR.

## Что не делать
- Не выпускать без проверки на копии рабочей базы, если менялась схема.
- Не править уже выпущенные миграции.
